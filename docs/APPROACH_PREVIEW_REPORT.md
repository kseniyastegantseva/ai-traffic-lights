# Управление с датчиком подъезда: что сделано и какие результаты

Дата: 2026-11-03. Ветка: `feature/approach-preview` (локально, не отправлялась в origin).

## 1. Зачем это делалось

Текущий результат проекта: интеллектуальный Queue-based выигрывает у Vehicle-actuated всего на 1–3 %, на уровне погрешности. Нужно было понять, что это: слабый метод или слабое сравнение, и можно ли улучшить показатели.

Вывод разведки: «1–3 %» — следствие плохо настроенного baseline, а реальный запас улучшения лежит в информации о машинах, которые ещё не встали в очередь, а не в более тонком сравнении очередей.

### Как работает контроллер

На каждом секундном такте он перебирает варианты «переключить фазу через 0…24 с» и «не переключать». Для каждого варианта он прогоняет короткую модель очередей на 50 с вперёд (rollout), учитывая машины из окна датчика. После переключения модель продолжает базовой политикой gap-out. Выбирается вариант с наименьшей суммой очередей по шагам. Максимальный зелёный 45 с сохранён, чтобы ось не голодала.

Датчик не меняет поток прибытий: его случайность зависит только от seed и номера автомобиля. Парность прогонов (общий поток у всех контроллеров) сохраняется.

## 3. Методика

- Перекрёсток: изолированный, 2 фазы, 4 подхода, обслуживание 2 с на машину, жёлтый 3 с, такт управления 1 с, пуассоновские прибытия, горизонт 1800 с.
- Сценарии (8): `symmetric_low`, `symmetric`, `symmetric_9`, `asymmetric_ns`, `asymmetric_ew`, `sudden_dominance_switch` (ниже пропускной способности) и `high_load`, `true_oversaturated` (перегрузка).
- 30 парных seed: development 12101–12130 (подбор), validation 13101–13130 (независимая проверка).
- Правило выбора baseline объявлено заранее: минимум среднего ожидания по шести сценариям ниже пропускной способности. Выбор записан в `outputs/approach_preview/development_selection.json` до запуска validation: Vehicle-actuated `va_min1_gap0`, Improved `imp20_min1`.
- Статистика: парный t-интервал 95 %, точный sign test, поправка Holm по всей таблице (88 контрастов validation).
- Метрика: среднее ожидание машин, завершивших обслуживание (при перегрузке есть правое цензурирование, как и в остальных сериях проекта).

### Главные контрасты (изменение ожидания, парное среднее, Holm p < 0,0001, если не указано иное)

1. **Настройка baseline важнее всего.** Настроенный VA лучше VA по умолчанию на 29–38 % во всех сценариях ниже пропускной способности. Именно здесь пропали «1–3 %»: сравнение шло с недонастроенным baseline.
2. **Идеальный датчик против настроенного VA:**
   - асимметричные сценарии и смена доминирования: −17,1…−17,8 %;
   - `symmetric`: −29,1 %;
   - `symmetric_9`: −17,5 %;
   - `symmetric_low`: −50,1 %.
3. **Ухудшенный датчик против настроенного VA:** −4,4…−5,3 % в асимметричных сценариях, −6,4 % в `symmetric`, −6,8 % в `symmetric_9` (Holm p = 0,0032), −19,5 % в `symmetric_low`.
4. **Абляция.** Тот же rollout без датчика (`preview_none_min2`) хуже настроенного VA на 3,5–5,5 % в пяти из шести сценариев ниже ёмкости (в `symmetric_9` различие незначимо: −0,2 %, p = 1,0). Значит, выигрыш даёт именно информация о подъезжающих машинах.
5. **Против Improved (`imp20_min1`):** идеальный датчик −30…−42 % ниже ёмкости (−73 % в `symmetric_low`).
6. **Перегрузка.** Датчик почти не помогает:

   | Сценарий | Идеальный датчик | Ухудшенный датчик |
   |---|---:|---:|
   | `high_load` | −1,9 % (p = 0,0008) | −1,6 % |
   | `true_oversaturated` | −0,5 % (p = 0,0002) | −0,4 % (p = 0,0038) |

   Максимальный красный при очереди остаётся 48 с, остаток в очереди сопоставим с baseline.

Development-серия дала тот же порядок эффектов. Окно 5 с при минимуме зелёного 4 с лишь немного слабее окна 10 с.

## 6. Ограничения и честные оговорки

- **Датчик идеализирован.** Нет модели времени проезда от камеры до стоп-линии, ложных срабатываний и перекрытий. Ухудшенный вариант лишь частично это покрывает. Эффект нельзя переносить на реальный перекрёсток без калибровки на данных.
- **Настроенный baseline нереалистичен.** Минимум зелёного 1 с (нижняя граница конфигурации) и gap 0 с. Gap дискретизирован по секундным тактам, поэтому gap 0, 0,5 и 1 с дали одинаковый результат. Rollout-контроллер использует минимум зелёного 2 с. Более реалистичные варианты (min 4–6 с) есть в development-таблицах.
- **Сетка настройки дважды упиралась в границу** и расширялась на development; для validation выбор уже зафиксирован.
- **В перегрузке выигрыш мал.** Датчик подъезда не заменяет пропускную способность.
- **Не обновлялись** dashboard и рукопись статьи.

## 8. Воспроизведение

```bash
# development
python scripts/create_approach_preview_configs.py
# validation (после development)
python scripts/create_approach_preview_configs.py --validation --preview-min-green 2
# запуск серии
traffic-light compare configs/approach_preview_ideal10_min2_val_1800.yaml
# анализ
python scripts/analyze_approach_preview.py --mode validation \
  --stems approach_preview_baselines_val_1800 approach_preview_ideal10_min2_val_1800 approach_preview_degraded10_min2_val_1800
```

Перед анализом нужно распаковать `outputs/approach_preview/*.json.gz` (`gunzip -k`): анализатор читает `.json`. Подробные таблицы: `outputs/approach_preview/validation_analysis.md` и `development_analysis.md`.
