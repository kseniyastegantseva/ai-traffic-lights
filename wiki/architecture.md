# Архитектура

## Среда выполнения

- Python-пакет: `traffic_light`
- CLI-точка входа: `traffic-sim`
- Dashboard: `app/dashboard.py`
- API: `app/api.py`
- Детектор изображения: `src/traffic_light/vision_detector.py`
- Веса YOLO: `models/visdrone_vehicles.pt`
- Исходный клон CV-модуля: `computer-vision/`
- Конфиги: YAML-файлы в `configs/`

## Интеграция фотографии и симуляции

Dashboard работает в два экрана. На первом пользователь загружает JPG/PNG/WebP-фотографию.
После загрузки `vision_detector.analyze_image_json()` автоматически формирует JSON-контракт
`north`, `south`, `west`, `east`, `total` в памяти. Четыре количества передаются в
`simulate_interactive_traffic()`: функция запускает общую SimPy-модель без новых прибытий,
задаёт их как начальные очереди, выбирает исходную ось по большей очереди и использует
`QueueBasedController` с UI-параметрами min-green 8 с, max-green 30 с и жёлтым 3 с.
Односекундная трасса SimPy преобразуется в кадры, сигналы и интервалы фаз для текущей
анимации. После моделирования dashboard переключается на экран результата.
Диагностические изображения и JSON не отображаются пользователю.

Для распознавания используется модель `computer-vision/models/visdrone_vehicles.pt`,
дообученная на VisDrone и содержащая классы `car`, `motorcycle`, `bus`, `truck` с
идентификаторами `0..3`. В проект она скопирована в `models/visdrone_vehicles.pt`,
а `vision_detector.py` сохраняет многошаговый алгоритм исходного репозитория:
автоматические зоны, детекцию полного кадра, масштабы x2/x3 и IoU-фильтрацию дублей.

Ручной ввод количества автомобилей удалён. Чтобы начать новый сценарий, пользователь
нажимает «Загрузить другую фотографию».

Пользовательский режим SimPy обслуживает только автомобили исходного снимка и не создаёт
новые прибытия. Исследовательские сравнения используют ту же физическую модель, но их
сценарии отдельно генерируют пуассоновские прибытия на всём горизонте; их сводки остаются
отдельным исследовательским представлением. Число машин на фото считается начальной
очередью только при допущении, что зона подхода соответствует ожидающим автомобилям;
одиночный кадр не измеряет поток и не подтверждает перегрузку. Метка `high_load`
интерактивного режима означает большую начальную очередь на снимке.

## Публичный CLI

```bash
traffic-sim run --config configs/base.yaml
traffic-sim train --config configs/ai.yaml
traffic-sim sweep --config configs/ai.yaml --episodes 10,25,50,100 --seeds 1,2,3,4,5
traffic-sim select-policy --config configs/ai.yaml
traffic-sim compare --config configs/experiment.yaml
```

## Основные компоненты

- `config.py` валидирует YAML-конфиги через Pydantic.
- `controllers.py` содержит фиксированные `fixed_8` / `fixed_15` / `fixed_35`, Webster split, vehicle-actuated, исходный `queue_based`, отдельный адаптивный `queue_based_improved`, а также экспериментальные `queue_based_empty_gap_fix`, `queue_based_max_red`, `queue_based_smooth_min_green`, `queue_based_hysteresis`, `queue_based_persistent_congestion` и `queue_based_axis_specific_congestion`. Варианты плавной рампы, гистерезиса, persistence и axis-specific наследуют Improved и меняют только правило выбора effective minimum green; состояние таймера/гистерезиса принадлежит экземпляру контроллера для одного прогона. Axis-specific включает длинный минимум, только если congestion есть на текущей обслуживаемой оси. Empty-gap использует proxy пустой очереди. Max-red использует наблюдаемое наличие очереди на красной фазе, ждёт minimum green и начинает переход заранее с учётом yellow clearance и односекундного шага наблюдений.
- `simulation.py` запускает SimPy-модель с общими воспроизводимыми потоками, начальными очередями и раздельным состоянием waiting / in_service / departed. `SimulationResult.max_red_with_queue_seconds_by_phase` отдельно сообщает максимальный red-интервал, пересекающийся с фактически ожидающей очередью; он отличается от непрерывного красного сигнала без запроса и от времени ожидания завершённого автомобиля.
- `experiments.py` выполняет парные сравнения по seed, считает интервалы разностей и sign test с Holm correction; исследовательские YAML находятся в `configs/piere_revision_*.yaml`.
- `gym_env.py` содержит минимальную Gymnasium-совместимую оболочку для будущего RL-обучения.
- `queue_audit.py` независимо воспроизводит seeded arrivals и FIFO обслуживание по архивным фазовым журналам; `statistics_audit.py` проверяет сводки, pair coverage, t-интервалы, sign test и Holm correction.

## Docker

Docker Compose содержит сервисы:

- `sim` — запуск экспериментов;
- `dashboard` — Streamlit-визуализация;
- `api` — FastAPI endpoint.

Текущий рабочий способ на машине пользователя: Docker Desktop установлен в Windows, а команды Docker доступны из PowerShell. В WSL установлен Docker CLI, но socket Docker Desktop не подключён к Ubuntu напрямую; если это понадобится, нужно включить WSL integration для дистрибутива `Ubuntu` в настройках Docker Desktop.

Для проверки без WSL bind mount используется `docker-compose.ci.yml`. Он не монтирует текущую папку внутрь контейнера и запускает код, скопированный в образ на этапе сборки.

Dockerfile разделён на два target:

- `base` — лёгкий образ для CLI-симуляции и экспериментов;
- `app` — образ для dashboard/API с дополнительными UI/API-зависимостями.

## Dashboard

Главный экран `app/dashboard.py` является пользовательским интерактивным симулятором. Он не
требует предварительно сгенерированных файлов из `outputs/` для сценария фото → детектор →
начальные очереди → SimPy → анимация. Исследовательская секция ниже на странице читает только
готовый компактный `outputs/piere_dashboard_data.json`; на загрузке приложения она не запускает
эксперименты. Этот JSON строится офлайн из сохранённых серий командой
`python scripts/build_piere_dashboard_data.py`.

Исследовательская визуализация сравнивает `fixed_15`, `fixed_35`, `fixed_webster`,
`vehicle_actuated` и `queue_based` на 1800/3600-секундных горизонтах. Она показывает среднее
ожидание с 95% CI, среднюю очередь, throughput, остаток ожидающих, среднюю очередь во времени,
фазы примерного seed и чувствительность к perception error. Полные per-run JSON остаются в
`outputs/`, но не загружаются внутрь Streamlit-процесса.

Входной контракт фронтенда — четыре целых неотрицательных числа: количество автомобилей
на подходах `north`, `west`, `south`, `east`. Эти автомобили образуют фиксированную начальную
очередь; новые автомобили во время демонстрации не создаются.

Модуль `interactive.py`:

- классифицирует начальные очереди как отсутствие движения, низкие, равномерные,
  пик север-юг, пик запад-восток или большую очередь на снимке;
- моделирует ровно два физических светофора: `north_south` для потока Юг–Север и
  `east_west` для потока Восток–Запад;
- хранит в каждом кадре отдельный цвет `red`, `yellow` или `green` для каждого светофора;
- запрещает одновременный разрешающий сигнал: при зелёном или жёлтом одного светофора
  второй светофор остаётся красным;
- выбирает первую зелёную фазу по наиболее загруженной оси;
- переключает фазы по давлению очередей с минимальным зелёным 8 секунд, максимальным
  зелёным 30 секунд и жёлтым интервалом 3 секунды;
- формирует секундную временную шкалу до проезда последнего автомобиля.

Dashboard показывает точное число автомобилей на каждом подходе, два трёхсекционных светофора,
их текущие сигналы,
оставшееся время фазы, модельное время, число проехавших машин, полное время работы
алгоритма, распределение зелёного времени и простой график оставшейся очереди.
В iframe-анимации доступны скорости воспроизведения `0.5x`, `1x`, `2x`, `4x` и `8x`;
скорость меняет только темп показа, а не расчётные секунды модели.

Длительность зелёной фазы зависит от очередей не как фиксированная формула "секунд на
машину", а через давление очередей. Текущая зелёная фаза длится минимум 8 секунд и максимум
30 секунд. Пока горит зелёный, раз в 2 модельные секунды с активной оси обслуживается до
двух автомобилей: по одному с каждого из двух направлений этой оси, если там есть очередь.
Поэтому один автомобиль на одном направлении требует около 2 секунд зелёного обслуживания,
а пара автомобилей на двух встречных направлениях может пройти за те же 2 секунды.

Для автомобилей используется спрайт-лист `app/assets/vehicle_sprites.jpeg`, предоставленный
пользователем. Он содержит 12 моделей в сетке 4×3. Dashboard встраивает изображение в iframe
как data URI, выбирает модель CSS-позиционированием, поворачивает её по направлению движения
и автоматически уменьшает размер машин при большой очереди. Количество HTML-моделей всегда
равно входному количеству автомобилей.

Два светофора отображаются как отдельные вертикальные трёхсекционные корпуса. JavaScript
активирует цвет каждой секции из полей `frame.signals.north_south` и
`frame.signals.east_west`, поэтому визуальный сигнал совпадает с состоянием модели.
Активная секция пульсирует CSS-анимацией `lampPulse`, при изменении цвета корпус кратко
подсвечивается анимацией `housingFlash`. Под каждым светофором JavaScript обновляет явную
подпись `КРАСНЫЙ`, `ЖЁЛТЫЙ` или `ЗЕЛЁНЫЙ`, поэтому состояние различимо не только по цвету.

Первое состояние обоих светофоров формируется на сервере сразу в готовом HTML: активная
лампа получает класс, цвет, прозрачность, свечение и текстовую подпись до выполнения
JavaScript. На каждом следующем кадре JavaScript повторно задаёт эти свойства напрямую
через `style`, а CSS-классы используются для анимации. Поэтому лампы не остаются серыми,
если выполнение скрипта внутри Streamlit iframe началось с задержкой.

## Состояние Streamlit

Dashboard хранит результат интерактивной симуляции в `st.session_state`. Поле
`dashboard_state_version` связано с текущей структурой кадров и интервалов фаз. После
изменения схемы старый результат автоматически распознаётся функцией `_is_current_result`
и пересоздаётся из значений формы. Это предотвращает ошибки hot reload, когда Python-код
уже обновился, а в сессии браузера остались объекты старых dataclass.

Перед встраиванием анимации кадры дополнительно нормализуются к текущему словарному
контракту. Если сохранённый или частично мигрированный объект не содержит поля
`signals` в результате `to_dict()`, dashboard берёт атрибут `signals` напрямую либо
использует безопасный красный сигнал для обоих светофоров. Поэтому iframe не падает с
`KeyError: 'signals'` при обновлении кода или устаревшем состоянии Streamlit.

Формирование таблицы вынесено в `_phase_rows`; функция поддерживает как актуальные поля
`axis`/`color`, так и прежнее поле `signal`, чтобы устаревший объект не приводил к падению UI.

Исследовательские JSON/CSV/Markdown-отчёты продолжают создаваться CLI-командой
`traffic-sim compare`, но больше не загружают основной пользовательский экран.

## RL-контур

`gym_env.py` задаёт Gymnasium-совместимую среду для выбора фазы светофора:

- observation: очереди `north`, `south`, `east`, `west` и текущая фаза;
- action `0`: фаза `north_south`;
- action `1`: фаза `east_west`;
- reward: отрицательная сумма очередей с небольшим штрафом за переключение фазы;
- episode: последовательность decision-интервалов внутри заданной длительности симуляции.

`rl.py` реализует первый обучаемый baseline: табличный Q-learning. Он нужен как прозрачная промежуточная ступень перед подключением Stable-Baselines3.

Команда:

```bash
traffic-sim train --config configs/ai.yaml --episodes 200
```

Результат сохраняется в `outputs/q_learning_policy.json`.

Команда:

```bash
traffic-sim sweep --config configs/ai.yaml --episodes 10,25,50,100 --seeds 1,2,3,4,5
```

запускает серию обучений Q-learning с разным числом эпизодов и seed, сохраняет отдельные policy-файлы `outputs/q_learning_policy_<episodes>_seed_<seed>.json` и формирует `outputs/q_learning_sweep.json`, `outputs/q_learning_sweep.csv`, `outputs/q_learning_sweep_summary.csv`, `outputs/q_learning_sweep.md`. Этот контур нужен для выбора разумной длительности обучения перед большим сравнением стратегий.

Команда:

```bash
traffic-sim select-policy --config configs/ai.yaml
```

читает `outputs/q_learning_sweep.json`, выбирает лучший конкретный policy-файл из лучшего sweep-варианта и копирует его в стандартный путь `outputs/q_learning_policy.json`, который использует контроллер `q_learning`.

После обучения policy может использоваться в SimPy-экспериментах через контроллер `q_learning`. Он читает Q-table из JSON, выбирает фазу с максимальным Q-значением, а для неизвестного состояния использует pressure-based fallback.
