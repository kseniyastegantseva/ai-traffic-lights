# Эксперименты

## Метрики

- Среднее время ожидания.
- Медианное время ожидания.
- Максимальное время ожидания.
- Средняя длина очереди.
- Пропускная способность в час.
- Количество остановок.
- Индекс справедливости между направлениями.
- Полуширина 95% доверительного интервала для среднего времени ожидания.

## Базовые стратегии

- `fixed`: переключение по фиксированной длительности фазы.
- `actuated`: переключение после минимального зелёного, если давление очереди на поперечном направлении выше.
- `ai`: интеллектуальная baseline-стратегия, выбирающая фазу с максимальным давлением очередей.

## Сценарий по умолчанию

Эксперимент по умолчанию запускает пять random seed для каждой стратегии из `configs/experiment.yaml`.

## Первый проверочный результат

Первое сравнение показало ожидаемую картину: адаптивная и AI-ориентированная стратегии сокращают среднее ожидание относительно фиксированного baseline. Сгенерированные файлы сохраняются локально в `outputs/` и игнорируются git.

## Демонстрационный сценарий равномерной нагрузки

Файл: `configs/demo_uniform.yaml`.

Сценарий задаёт одинаковую интенсивность потока по всем направлениям: 6 автомобилей в минуту для `north`, `south`, `east` и `west`. Он нужен как первый стабильный демонстрационный режим без перекоса спроса, на котором удобно показывать полный цикл:

- запуск стратегий `fixed`, `actuated`, `ai`;
- сохранение подробных запусков в `outputs/demo_uniform_results.json`;
- сохранение сводной таблицы в `outputs/demo_uniform_summary.csv`;
- генерация единого Markdown-отчёта `outputs/demo_uniform_report.md`;
- просмотр результатов в dashboard.

Команда запуска:

```bash
traffic-sim compare --config configs/demo_uniform.yaml
```

На первом запуске лучшей стратегией стала `actuated`: среднее ожидание 7.83 с против 12.72 с у `fixed`, улучшение около 38.5%.

## Набор исследовательских сценариев

Файл: `configs/experiment_suite.yaml`.

Это следующий этап после одиночного demo-сценария. Набор содержит пять сценариев:

- `uniform_demo` — равномерная нагрузка 6 авто/мин по каждому направлению;
- `low_load` — низкая нагрузка 3 авто/мин по каждому направлению;
- `morning_peak_ns` — утренний пик по направлению north/south;
- `evening_peak_ew` — вечерний пик по направлению east/west;
- `oversaturated` — перегруженный перекрёсток 9 авто/мин по каждому направлению.

Команда запуска:

```bash
traffic-sim compare --config configs/experiment_suite.yaml
```

Результаты сохраняются в:

- `outputs/experiment_suite_results.json`;
- `outputs/experiment_suite_summary.csv`;
- `outputs/experiment_suite_report.md`.

## Исследовательские графики

В нижней части второго экрана dashboard, после симуляции, автоматически
показывается блок «Исследовательские графики». Первый экран загрузки фотографии
при этом не меняется. Блок читает `outputs/experiment_suite_results.json` и показывает:

- по умолчанию сценарий, соответствующий нагрузке, определённой на фотографии;
- компактные кнопки для переключения на остальные сценарии без добавления
  нескольких графиков одновременно;
- крупные интерактивные Plotly-графики с масштабированием, наведением и
  выгрузкой данных;
- пояснение того, что означают стратегии `fixed` и `ai`.

В пользовательском сравнении отображаются только две стратегии: `fixed` —
обычный стандартный светофор, и `ai` — интеллектуальный алгоритм проекта.
Адаптивная стратегия остаётся внутренним дополнительным baseline в полном
экспериментальном наборе, но в графики пользовательского экрана не выводится.

- среднее время ожидания автомобиля с 95% доверительным интервалом;
- пропускную способность по сценариям;
- сокращение ожидания относительно `fixed` в процентах;
- среднюю длину очереди;
- динамику очереди во времени с усреднением по random seed;
- распределение среднего ожидания по запускам и random seed.

При первом открытии второго экрана dashboard автоматически запускает
`configs/experiment_suite.yaml`, сохраняет результаты эксперимента и строит
графики. Повторный запуск не выполняется, если актуальный JSON уже существует.
Сравнение выполняется внутри одного сценария: стратегии получают одинаковые
входные потоки и random seed. Поэтому различия в количестве автомобилей между
сценариями не искажают сравнение. Основной показатель нормирован на один
автомобиль — среднее время ожидания.

Первичный прогон показал, что `actuated` и `ai` во всех сценариях сокращают среднее ожидание относительно `fixed`. Наиболее заметные улучшения находятся в сценариях направленных часов пик и низкой нагрузки.

## Аналитический слой отчёта

Единый отчёт теперь содержит не только сводную таблицу, но и аналитические секции:

- рейтинг стратегий внутри каждого сценария по среднему времени ожидания;
- агрегированную сводку по стратегиям: число побед, средний ранг, среднее ожидание, среднее улучшение к `fixed`, средняя очередь и индекс справедливости;
- сравнение `ai` против `actuated` по каждому сценарию.

Текущий вывод по `experiment_suite`: `actuated` имеет лучший средний ранг и 3 победы из 5 сценариев, а `ai` показывает лучшее среднее ожидание и выигрывает в сценариях низкой нагрузки и утреннего пика north/south. Это означает, что текущая AI baseline-эвристика перспективна, но ещё не является устойчиво лучшей стратегией во всех режимах.

## Первый обучаемый AI baseline

Добавлен табличный Q-learning baseline. Он обучается не как финальная промышленная модель, а как прозрачный и воспроизводимый первый шаг к интеллектуальному управлению:

- состояние дискретизируется по длинам очередей и текущей фазе;
- действия соответствуют выбору одной из двух фаз;
- reward минимизирует суммарную очередь и штрафует лишнее переключение;
- policy сохраняется в JSON для анализа и последующего сравнения.

Команда:

```bash
traffic-sim train --config configs/ai.yaml --episodes 200
```

После обучения policy можно включить в единый эксперимент:

```bash
traffic-sim compare --config configs/experiment_suite_rl.yaml
```

`configs/experiment_suite_rl.yaml` добавляет к `fixed`, `actuated` и `ai` четвёртый контроллер `q_learning`, который использует сохранённую policy из `outputs/q_learning_policy.json`.

## Sweep обучения Q-learning

Для экспериментального подбора числа эпизодов обучения добавлена команда:

```bash
traffic-sim sweep --config configs/ai.yaml --episodes 10,25,50,100 --seeds 1,2,3,4,5
```

Она последовательно обучает несколько Q-learning policy и сравнивает их в evaluation-прогоне Gymnasium-среды. Основной ориентир на этом этапе — `evaluation_average_queue`: чем меньше средняя очередь, тем лучше policy справляется с разгрузкой перекрёстка в проверочном эпизоде.

При передаче нескольких seed команда дополнительно считает агрегированную сводку по каждому значению episodes: средние значения метрик, стандартное отклонение средней очереди и полуширину 95% доверительного интервала. Это делает sweep пригодным для выбора параметров обучения в научном отчёте, а не только для ручной отладки.

Результаты сохраняются в:

- `outputs/q_learning_sweep.json`;
- `outputs/q_learning_sweep.csv`;
- `outputs/q_learning_sweep_summary.csv`;
- `outputs/q_learning_sweep.md`;
- `outputs/q_learning_policy_<episodes>_seed_<seed>.json`.

Чтобы передать лучший результат sweep в общий эксперимент, используется команда:

```bash
traffic-sim select-policy --config configs/ai.yaml
```

Она выбирает лучший `episodes` по агрегированной средней очереди, затем конкретный лучший seed-прогон внутри этого `episodes` и копирует его policy в `outputs/q_learning_policy.json`.

Проверочный multi-seed sweep на `2,3` эпизода и seed `11,12` показал ожидаемо сильную нестабильность на малом числе эпизодов. Это нормально для раннего табличного RL baseline и означает, что следующий научный шаг — запускать sweep на большем диапазоне episodes и затем проверять выбранную policy в `configs/experiment_suite_rl.yaml`.
